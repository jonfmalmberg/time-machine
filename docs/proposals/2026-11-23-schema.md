# Proposal: the data model (roadmap 2.3)

**Status:** proposal by Claude, 23 November 2026. Not agreed, nothing built. It follows from the data inventory ([`../research/2026-11-23-data-inventory.md`](../research/2026-11-23-data-inventory.md)) and is what the research tiers ([`2026-11-23-research-tiers.md`](2026-11-23-research-tiers.md)) need in order to be stored.

## What is wrong with the model today

A song is a pair of texts. The same recording in a genre playlist, a decade list and a year list is three unrelated entries: the inventory found 186 spelled differently across files. Nothing can carry a weight, a pass number or a piece of evidence, because there is no record to hang it on. Most entries are positional lists that only the code can read. Sources exist for year lists only.

## The model in one picture

```
 artist ──< credited on >── song ──< song-in-scope >── scope ── research state
                             │            │              │
                          release      evidence      test runs
                                     (string, where,
                                      when, checked)
 scope is one of:  genre   |   country + year
 genre ── parents, tradition, family, region, where and when it peaked   (as today)
 place ── country, city, region                                           (as today)
```

Seven kinds of record. Four are new (song, artist, song-in-scope, evidence); the others exist and keep their keys.

## The records

### Song
One recording: the thing that plays. A later cover or a re-recording is a different song.

| Field | Meaning |
| :- | :- |
| `id` | Stable key, never reused (see Keys) |
| `title` | As streaming services show it, in its original script |
| `title_rom` | Romanised or international form, where different |
| `artists` | Artist ids, in credit order |
| `year` | Year of release |
| `written` | Year written, where it differs and matters (standards, traditional songs) |
| `minutes` | Length, so listening time can be a target |
| `mbid` | MusicBrainz recording identifier, when found. Lets cover art and outside data attach later |
| `fame` | How widely known anywhere, 0 to 1. Separate from how characteristic it is of any scope |

### Artist
`id`, `name`, `name_rom`, `country`, `mbid`. Nothing else until something needs it.

### Scope
The unit of research and of testing.

| Field | Meaning |
| :- | :- |
| `id` | `g:swing` for a genre; `c:JP:1985` for a country-year |
| `size` | Estimate of how many songs fit: low, high, core, basis, confidence |
| `targets` | This scope's own song count or minutes per tier |
| `tier` | Reached, and accepted (passed its acceptance tests) |
| `passes` | Each pass: number, date, who ran it, what it added |
| `tests` | Ids of the recorded test runs on this scope |

### Song-in-scope
The link that says a song belongs to a scope, and how much. This is where weights live.

| Field | Meaning |
| :- | :- |
| `song`, `scope` | The two ids |
| `role` | Genre: `intro`, `peak`, `reference`, `near miss`. Country-year: `home` or `foreign` |
| `w_evidence` | 0 to 1 from sources: chart position, number of independent sources |
| `w_synth` | 0 to 1 from synthetic listeners |
| `w_human` | 0 to 1 from real listeners; empty until milestone 8 |
| `rank` | Position by the blended weight; computed, not typed |
| `pass` | The pass that added it |
| `evidence` | Ids of the evidence records that support this link |
| `note` | For example "deliberate early pick", so a date outside the scope is not a fault |

### Evidence
One per claim, kept even after the site is gone.

| Field | Meaning |
| :- | :- |
| `id` | Stable key |
| `url`, `title` | Where it was found |
| `text` | The exact string from the page |
| `read` | Date it was read |
| `check` | `found`, `not found`, `source gone`, `erroneous`, or empty if not yet checked, with the date |

### Genre and place
As today, with named fields instead of list positions. Their ids do not change, so saved trips and requests keep working.

## Keys

A key must be stable, must not collide when two helpers research in parallel on separate branches, and must not depend on a spelling that may later be corrected.

- **Song:** `s_` plus ten characters derived from the first artist, the title and the year as first recorded, normalised (case, accents, spacing, "feat." removed). Two helpers who find the same song produce the same key; a merge joins them instead of duplicating. The key is then frozen: correcting the spelling later does not change it.
- **Artist:** `a_` plus ten characters from the normalised name as first recorded.
- **Evidence:** `e_` plus ten characters from the address and the string.
- **Scope, genre, place:** readable keys as shown, as today.

## Files

One file per scope, holding its research state, its song links and the songs and evidence they refer to, so a helper branch touches only the scopes it worked on and two branches rarely conflict:

```
data/scopes/g/swing.json
data/scopes/c/JP/1980.json      (ten country-years of a decade in one file)
data/genres.json, data/places.json, data/artists.json
```

A song that appears in several scopes is written in each, under the same key; the build joins them into one record and reports any disagreement between copies (date, spelling) as a fault. That keeps scope files self-contained for helpers and makes the identity test automatic.

How these files reach a visitor's browser (all at once as now, or loaded when a scope is opened) is the separate proposal 2.10. This layout works for both.

## Moving to it without breaking the site

1. Convert today's files into the new ones by script, generating keys and joining songs that match after normalisation. The 186 spelling differences and 184 artist-credit candidates are listed for a decision each, not merged blindly.
2. The build then produces, from the new files, exactly the data shape the page reads today. The page does not change. The check is that the built page is identical before and after, apart from the corrected spellings.
3. Features then move to reading the new shape one at a time (weights, tiers, evidence), each as its own change.

Step 2 is the reason the move is safe: the model can be replaced under the site in one step, and the site catches up at its own pace.

## Decisions for the owner

1. **A song is a recording, not a composition.** "Summertime" by two singers is two songs. The alternative (one work, many versions) is truer to music history but doubles the model, and playlists play recordings.
2. **Keys derived from artist, title and year**, frozen after first use, with the MusicBrainz identifier stored beside them where found. The alternative is to use MusicBrainz identifiers as the key, which fails for the many songs it does not have.
3. **One file per scope, songs repeated across scope files and joined at build.** The alternative is one central song file, which every helper branch would edit and conflict on.
4. **Three weight parts stored, the blend computed.** Follows principles 16 and 20.

## What this does not cover

Feel (mood, tempo: 2.5), the prominence formula (2.6), regions (2.4), delivery to the browser (2.10), and people's data in the database, which is unchanged.
