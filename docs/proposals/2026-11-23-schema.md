# Proposal: the data model (roadmap 2.3)

**Status:** proposal by Claude, 23 November 2026, revised the same day after the owner's first reading. Settled by him: a song is a recording; compositions and sampling are linked from the start; keys are standalone values; songs live in central files and a scope only defines research; duplicates are resolved when the master table is put together. Not yet seen by him: the definitions of country and year, and the records for artists, places, genres and the tree, which the first draft left as "as today". Nothing is built. The site keeps running on today's files until the move.

It follows from the data inventory ([`../research/2026-11-23-data-inventory.md`](../research/2026-11-23-data-inventory.md)) and is what the research tiers ([`2026-11-23-research-tiers.md`](2026-11-23-research-tiers.md)) need in order to be stored.

## What is wrong with the model today

A song is a pair of texts. The same recording in a genre playlist, a decade list and a year list is three unrelated entries: the inventory found 186 spelled differently across files. Nothing can carry a weight, a pass number or a piece of evidence, because there is no record to hang it on. Most entries are positional lists that only the code can read. Sources exist for year lists only.

## The model in one picture

```
 composition ──< performed as >── song ──< song-in-scope >── scope ── research state
                                   │  │           │             │
              artist ──< credit >──┘  └─< relation >─ song   test runs
                │                     (samples, remix of,      
              place                    version of)          evidence (exact string,
                                                             where, when, checked)

 scope is one of:   genre   |   country + year
 genre ──< influence >── genre        genre ──< presence >── place and years
 genre ── tradition ── family         place:  region > country > city or area
```

## Keys

Every record has a standalone key: a short prefix and a random value (`s_7k2m9q4x1c`), made by a script when the record enters the master table. A key says nothing about the record and never changes. Artist, title and year are attributes, not identity: two recordings can share all three (an album version and a single version, a same-year remix), and one recording can be listed under several spellings.

Helpers never make keys. They hand back candidate records without keys. Putting the master table together is one step, run by the lead: it matches each candidate against existing records, gives new ones a key, and lists the uncertain matches (same title with a slightly different spelling, same artist and year but possibly a different recording) for a decision instead of merging or duplicating blindly. Uniqueness is checked there and nowhere else.

Genres, countries, regions, families and traditions keep the readable keys they have today (`swing`, `JP`, `eur`), because saved trips and requests already point at them.

## Songs

### Song
One recording: the thing that plays.

| Field | Meaning |
| :- | :- |
| `id` | Standalone key |
| `title` | As streaming services show it, in its original script |
| `title_rom` | Romanised or international form, where different |
| `aliases` | Other spellings and listed titles of the same recording ("- Remastered 2009", a translated title). Used for matching and search, never shown as separate songs |
| `credits` | Artist ids in credit order, each with a role: main, featured, with |
| `released` | First release of this recording anywhere: year, and month where known |
| `country` | Only when it differs from the first artist's country (see Country) |
| `lang` | Language sung, or `instrumental` |
| `minutes` | Length |
| `composition` | Composition id, where known |
| `mbid` | MusicBrainz recording identifier, where found |
| `fame` | How widely known anywhere, 0 to 1 |

### Composition
The song as written, apart from any one recording. It lets a composition be followed through time: every cover, in every country and decade it turned up in.

| Field | Meaning |
| :- | :- |
| `id`, `title`, `title_rom` | |
| `writers` | Artist ids, or text where the writer has no artist record. `traditional` where there is none |
| `written` | Year written or first published |
| `mbid` | MusicBrainz work identifier, where found |

A song with no known composition simply has none. Research records it when the source states it, and does not go looking.

### Relation between two songs

| Kind | Meaning |
| :- | :- |
| `samples` | This recording uses part of that one |
| `remix of` | A remix or edit of that recording |
| `version of` | Another recording of the same piece by the same artist: live, re-recorded, single against album version |

Covers need no relation: two songs with the same composition are covers of each other. Each relation carries its evidence like any other claim.

### What counts as the same recording

| Case | Same song? | Handling |
| :- | :- | :- |
| Remaster | Yes | One song. The remaster's listed title goes in `aliases`. `released` stays the original year |
| Reissue, compilation appearance | Yes | One song |
| Remix, edit, extended mix | No | Its own song, `remix of` the original |
| Live recording, re-recording ("Taylor's Version") | No | Its own song, `version of` the original, same composition |
| Single version against album version | No, if they differ audibly | Two songs, `version of`. A list uses the one that was the hit |
| Cover by another artist | No | Its own song, same composition |

This matches how MusicBrainz draws the line, which matters because its identifiers are stored: "separate recordings should not be created for remastered tracks", while "different performances of the same work should always be given separate recordings" and remixes "should always be given a new recording" (MusicBrainz, Style / Recording, https://musicbrainz.org/doc/Style/Recording, read 23 November 2026).

### Year

There are three different years, and they are kept apart.

| Year | Lives on | Meaning |
| :- | :- | :- |
| `released` | The song | First release of that recording, anywhere. Never the remaster or reissue date |
| `written` | The composition | When the piece was written. This is what matters for a standard recorded decades later |
| The year of a country-year scope | The song-in-scope link | The year it was heard there. Often not the release year: a December release is next year's hit; a song can chart abroad years later, or again after a film or a viral revival |

The last one is why the listener test on Japan 1998 complained about a song released in December 1998 "but really a 1999 hit": with one year per song the data cannot say both things.

### Country

"Where is this song from" has several possible answers. One is needed for the app, and it is defined once.

| Candidate | Used? | Why |
| :- | :- | :- |
| **The artist's scene**: the country whose music world the artist worked in and is identified with | **Yes: this is `country`**, kept on the artist | It is what "home-grown" means to a listener, and what the home or foreign split in a year list needs |
| Where the artist was born or grew up | Kept on the artist as `born_in` when it differs | It matters for emigrant journeys and for music carried abroad, but it is not what makes a song local |
| Where the recording was made | Not tracked | A studio's location rarely matters to a listener. A relation can be added later if a use appears |
| Where it was a hit | Not a property of the song | That is exactly what country-year scopes record |

An artist whose scene changed (moved abroad and built a second career there) has dated entries: `country` is a list of country and from-year, and a song takes the one in force at its release. A song can override it with its own `country` in the rare case the artist's does not fit that recording.

MusicBrainz defines its artist area the same way ("the area with which an artist is primarily identified with. It is often, but not always, its birth/formation country", MusicBrainz, Artist, https://musicbrainz.org/doc/Artist, read 23 November 2026), so its value can be taken as a first answer and checked.

Country alone does not settle "local". Canada's lists failed francophone listeners because one national list cannot open well for two language communities. `lang` on the song, and a city or area on the artist, are what let a list for Montréal lead with francophone songs.

## Artist

| Field | Meaning |
| :- | :- |
| `id` | Standalone key |
| `name`, `name_rom`, `aliases` | As for songs |
| `kind` | Person, group, orchestra or choir, other |
| `country` | The scene, as defined above. One entry, or dated entries where it changed |
| `home` | City or area id within that country, where known (Liverpool, Montréal) |
| `born_in` | Country, when different from `country` |
| `active` | First and last year active |
| `members`, `member_of` | Artist ids, where known. Lets a solo career be tied to a band |
| `mbid` | MusicBrainz artist identifier, where found |

## Places

Three levels, as today, with named fields.

### Region
`id` (`eur`), `name`, `colour`. The ten regions. Whether ten is the right number and where their borders run is proposal 2.4.

### Country
| Field | Meaning |
| :- | :- |
| `id` | ISO two-letter code |
| `name`, `names` | Name, and dated historical names where the country was called something else |
| `region` | Region id |
| `langs` | Main languages, first is the default for prompts |
| `from`, `to` | Years it existed, for states that began or ended (Yugoslavia, East Germany). Today the data has no way to say this |
| `successor_of` | Country ids, so music from a former state is found under the present one |
| `map_names` | Names used by the world outline, for matching shapes |

### City or area
| Field | Meaning |
| :- | :- |
| `id` | Standalone key. Today's key is `ISO:name`, which breaks if a name is corrected; the old form is kept as an alias so saved trips still resolve |
| `name`, `names` | Name, and dated historical names |
| `country` | Country id |
| `kind` | City or area |
| `lat`, `lon`, `radius_km` | Position; radius for an area |
| `founded`, `ended` | Years it appears and disappears |
| `size` | 1 to 3: the map zoom at which it appears |
| `lang` | Only where it differs from the country's |

The unexplained `x` flag and the unread `note` in today's city data are dropped; `x`'s effect (appear one zoom step earlier) is folded into `size`.

## Genres and the tree

### Genre
| Field | Meaning | Today |
| :- | :- | :- |
| `id` | Readable key, unchanged | `nodes` position 0 |
| `name`, `aliases` | | position 1 |
| `tradition` | Tradition id | `tradOf` |
| `region` | Region id of its origin | position 2 |
| `origin` | Place: a city or area id where there is one, else a country, with the text shown to people | positions 5 to 7, free text and coordinates |
| `began`, `ended` | Start year; end year or still alive | position 4, `ends` |
| `attested` | True when `began` is only the first written record of something older | Missing today; the tree cannot say "older than records" |
| `definition` | Active years, the sound, what to listen for | `defs` |
| `judgements` | Significance, ease of listening, how widely known, intrigue, each 1 to 5, each with who or what set it and when | `scores`, with no record of how they were set |
| `note` | One line for the tree | `notes` |

Reference tracks, near misses and the playlist are no longer inside the genre: they are song-in-scope links with a role.

### Tradition and family
`tradition`: `id`, `name`, `family`. `family`: `id`, `name`, `order` (top to bottom on the tree). 163 traditions in 20 families, as today.

### Influence: the lines of the tree
One record per line from one genre to another.

| Field | Meaning | Today |
| :- | :- | :- |
| `from`, `to` | Genre ids | `edges` |
| `kind` | `parent` (the closest ancestor: one per genre, none for roots), `influence` (a lesser line) | Two files that overlap: parents in `nodes`, weights 1 and 0.4 in `edges`, with no stated relation between them |
| `year` | When the influence happened, where known | Missing |
| `evidence` | Like any claim | Missing: no line on the tree has a source today |

### Presence: where and when a genre was heard
One record per genre and place, replacing the two parallel files that say this by region and by country.

| Field | Meaning | Today |
| :- | :- | :- |
| `genre`, `place` | Genre id; a country, or a region where no finer answer exists | `st`, `cnt` |
| `kind` | `origin`, `peak` (big there at the genre's peak), `later` (arrived afterwards) | list positions |
| `from`, `to` | Years | peak years; arrival year |
| `strength` | How big it was there, 0 to 1 | Implied by list order: the first three countries count most. An order that carries meaning is a fault waiting to happen |
| `evidence` | Like any claim | Missing |

### What is not data
The tree's layout (rows, lane order) and the zoom tier are computed from the data by the build, not stored as if they were facts about music. Today they are stored, and `tier`'s values have no recorded origin. The proposal is to compute tier from significance and layout by the existing method, and keep only the inputs.

## Research records

### Scope
A scope defines research and holds its state. It holds no songs.

| Field | Meaning |
| :- | :- |
| `id` | `g:swing` for a genre; `c:JP:1985` for a country-year |
| `size` | Estimate of how many songs fit: low, high, core, basis, confidence |
| `targets` | This scope's own song count or minutes per tier |
| `tier` | Reached, and accepted |
| `passes` | Each pass: number, date, who ran it, what it added |
| `tests` | Ids of the recorded test runs |

### Song-in-scope
| Field | Meaning |
| :- | :- |
| `song`, `scope` | The two ids |
| `role` | Genre: intro, peak, reference, near miss. Country-year: home or foreign |
| `w_evidence`, `w_synth`, `w_human` | Three weight parts, 0 to 1 each |
| `rank` | Computed from the blend |
| `pass` | The pass that added it |
| `evidence` | Evidence ids |
| `note` | For example "deliberate early pick" |

### Evidence
`id`, `url`, `title`, `text` (the exact string from the page), `read` (date), `check` (found, not found, source gone, erroneous, or not yet checked, with the date). Any record or field can point at evidence: a song's release year, an artist's country, an influence line.

## Files

```
data/songs/…            central, split into files by key so no file grows without limit
data/artists/…          the same
data/compositions.json, data/relations.json
data/scopes/g/swing.json, data/scopes/c/JP/1980.json     research state only
data/links/g/swing.json, data/links/c/JP/1980.json       song-in-scope links
data/evidence/…
data/genres.json, data/influence.json, data/presence.json
data/traditions.json, data/families.json
data/regions.json, data/countries.json, data/cities.json
```

Only the step that puts the master table together writes to `data/songs`, `data/artists` and `data/evidence`. Helpers hand back candidates in `work/`. That is what makes central files workable with several helpers: there is one writer.

How these files reach a visitor's browser is proposal 2.10.

## Moving to it without breaking the site

1. Convert today's files by script. Songs that match after normalising become one record; the 186 spelling differences and 184 artist-credit candidates are listed for a decision each.
2. The build then produces, from the new files, exactly the data shape the page reads today. The page does not change. The check is that the built page is the same before and after, apart from corrected spellings.
3. Features move to the new shape one at a time.

## Where Claude disagrees or adds

Nothing in the owner's changes is disagreed with. Two consequences of them, stated so they are not a surprise:

- **Standalone keys mean matching is a judgement, made at one point.** With derived keys two helpers finding the same song would have joined automatically. Now the joining step has to recognise it, and its uncertain cases need a person or a careful agent. That is the right trade, because the automatic join was wrong exactly in the cases that matter (remixes, two recordings in one year), but it makes that step the place where data quality is won or lost, and it needs its own test.
- **Compositions and sampling are recorded when found, not hunted.** Making them a required field would multiply the research per song for something most playlists never use.

Added beyond what was asked, each because a known failure needs it: `lang` on songs (the Canada result), month in `released` and a separate year on the link (the Japan 1998 result), `attested` on genres (oral traditions), `from` and `to` on countries (former states), `strength` on presence in place of meaningful list order.

## Decisions for the owner

1. **Country means the artist's scene**, kept on the artist, dated where it changed, with `born_in` beside it and recording location not tracked.
2. **Three years kept apart:** release on the song, written on the composition, heard-there on the link.
3. **Layout and tier computed, not stored.**
4. **Parents and influence lines become one kind of record** with a `kind`, and every line can carry evidence.
5. **Cities get standalone keys**, with today's `ISO:name` kept as an alias.

## What this does not cover

Feel (mood, tempo: 2.5), the prominence formula (2.6), which regions exist (2.4), delivery to the browser (2.10), and people's data in the database, which is unchanged.
